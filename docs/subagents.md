# DeepSeek subagents

Tenjin can offer DeepSeek V4.1 Flash 1017, a cheap model, for helper work. Your parent keeps its model and final accept/veto. DeepSeek is the model that runs these jobs today, and it receives a job only after the parent accepts its offer: the accepted assignment, the instructions that apply and the job's tool results, through Tenjin ([privacy](https://tenjin.sh/privacy)). [Data and permissions](#data-and-permissions) lists every recipient and what a worker can read, and [Charges and limits](#charges-and-limits) the fees and the per-job cap. Ordinary implementation and scoped review can qualify; planning stays native. Repository instructions and model/privacy restrictions still apply.

## Setup and controls

Fresh installations ask whether to use a cheap model for eligible subagent jobs, in three lines that end with a link to this page. **Keep off** is the default. **Turn on** enables routing for each session's qualified native workspace and then prints the sharing and charges once. A job's routing, inference and web searches together cost up to your per-call spend limit as it stands at each offer ($1 unless you chose another), and your daily budget applies on top. A scripted fresh install passes `tenjin install --yes --subagents on` to opt in or `--subagents off` to save off. The flag answers that question only: on a profile that already exists it is refused and nothing changes, so use the `tenjin config subagents` commands below there. Opening another repository uses that session's current native scope; the folder where installation ran supplies no directory grant. Each job freezes its qualified scope and rechecks it before tools, inference and continuation.

Existing users keep their settings, including off choices and named-directory consent. Updating, refreshing or adding another host does not enable DeepSeek for an existing profile. The parent still accepts or vetoes each offer.

```sh
tenjin config subagents off
tenjin config subagents on --repository /path/to/repository
tenjin config subagents on --repository /path/to/repository --max-job 0.50
```

The explicit `on --repository` command records consent for the named directory and descendants, the configured router origin, the recipients (Tenjin, DeepSeek and Exa) and the rule for a job's cap. With no `--max-job`, the cap is your per-call spend limit as it stands at each offer, so a changed limit changes the next offer, up or down, and lowers a running job's remaining cap at once. `--max-job <USD>` names a lower ceiling: the cap is then the smaller of that ceiling and the limit, and a higher limit never lifts a ceiling you named until you run the command again. A consent saved before this rule keeps its $1 ceiling as a named one. Where the cap is under $0.086866, what one model call and its routing fee need, no job is offered: `tenjin config subagents why` shows `job_cap_too_low`, and `tenjin config subagents on` refuses to turn routing on under such a limit and names the command that raises it. Repeat for another repository to retain both, or name a containing workspace. This selects named-directory scope instead of following future workspaces automatically. Local GitHub origin names for qualifying directories and their direct child repositories accompany offers so the parent can match GitHub tasks to paths. Names grant no filesystem permission or additional disclosure scope; stale names are dropped when their local origins change or disappear. A project can disable routing, but cannot grant consent or raise your money limits. Unsupported older consent must be renewed explicitly. That includes a consent given before a worker could read your `~/.claude` folder (see Data and permissions), and one that names Tenjin and DeepSeek but not Exa: it stops qualifying, no offer is made, `tenjin config subagents why` shows `consent_outdated`, and running the `on --repository` command again shows the current terms and renews it for the directories you name.

### Claude Code on Linux and Windows

On Linux, DeepSeek workers use Claude Code’s native shell sandbox. Install the sandbox dependencies for your distribution and check that Claude Code reports a working sandbox. See the [Claude Code sandbox documentation](https://code.claude.com/docs/en/sandboxing) for Linux and WSL2 requirements.

On native Windows, DeepSeek workers use the native Claude shell tools under a dedicated standard local Windows account. Git Bash and PowerShell have the access Windows grants to that account, including network access and files outside the selected repository. Keep the controller’s Tenjin data and sign-in credentials in its private profile. Only share workspaces and Claude configuration that you are comfortable exposing through the worker’s tool results. Windows setup requires a separate opt-in. [Windows setup instructions](../scripts/windows-worker/README.md)

## Data and permissions

Routing sends the assignment and bounded parent context to Tenjin and TypeSafe before acceptance. Claude Code can prepare a local worker while the offer is open. The worker gets its assignment only when the parent accepts. Vetoing or cancelling the offer, letting it expire, or ending the parent session stops that process. A routing request is at most 16 KB: Tenjin gives up parent context to fit it, the oldest message first, and never cuts the assignment, so a call whose assignment alone is larger stays native. After acceptance, applicable instructions, assignments and tool results reach DeepSeek through Tenjin. A worker's web search queries, and the address of a public page its WebFetch could not fetch, reach Exa (see Charges and limits). Known secrets are masked; sensitive prose is not guaranteed anonymous. Server replay content expires after 24 hours; financial and continuation authorization records persist.

The Claude worker retains native settings, rules, hooks, MCPs, CLIs and tool permissions in its workspace, including uncommitted changes. Global auto-memory is disabled for this worker. Native-workspace consent follows the host's qualified current directories and access exceptions. Named-directory consent makes every named directory a working directory too, so a session in one repository of a named workspace reaches its sibling repositories; their linked git worktrees inside the named directories are added at job start, so the worker can commit in them. A native additional directory outside the named directories is denied to the worker and listed in the offer, and the offer still stands; native read or write exceptions outside them keep work native. On Linux and macOS, shell confinement must be enforceable. Managed-only read-path policies, disabled or excluded sandbox commands, and startup paths containing `*`, `?`, `[` or `]` keep work native. On Windows, the offer requires the separate native shell grant and compatible Claude settings. Scope is checked before assignment, tool use and inference. Your parent's endpoint, saved login and Remote Control stay in place. Unsupported authority or host-controlled authentication keeps work native. A provider refusal at worker startup can follow an already-paid routing fee.

On Linux and macOS, the worker loads your global Claude Code configuration as a native session does, so your personal `~/.claude/CLAUDE.md` is in its instructions, unless it runs as `Explore` (see below). As a native subagent can, its file tools and commands read the skills, plugins (with their data folders), agents, commands and rules under `~/.claude`, every session transcript and project memory under `~/.claude/projects`, your prompt history `~/.claude/history.jsonl`, and your `~/.claude/settings.json` and `settings.local.json`; they cannot write them. What it reads there, other projects' sessions and memory included, can reach Tenjin and DeepSeek. The values in those settings files' `env` blocks, and in the `env` block Claude Code hands to the worker's commands, become `[env:NAME]` by the env file rules below: the files are read when the job starts and again before anything is forwarded, a settings file that cannot be parsed at the start stays unreadable, and one that stops parsing during the job stops it. Transcripts and history are not scanned, so a secret pasted or printed in an earlier session is sent as written unless it has a known token shape. The rest of `~/.claude` stays closed: the credentials file, settings backups (whose old values are not scanned), session state such as `debug` and `file-history`, `tenjin-loops` outside your consented directories and a skill's files where its folder links outside `~/.claude`; so does `~/.claude.json`. In the working directories, a repository's tracked `.claude/settings.json`, its own or a nested one, is readable as a native subagent reads it, with its `env` values replaced by the env file rules below; one that cannot be parsed at job start stays unreadable. On Linux, which has no watcher for files made during a job, these files stay unreadable to the worker. Its file tools never write one, and its commands cannot write the working directory's own, so a merge or checkout that must rewrite that file fails at that write, as a native sandboxed command does before it asks to run unsandboxed, which a worker cannot. Every repository's `.claude/settings.local.json` and `.mcp.json` stay closed, and so does a project settings file outside the working directories. Each job has its own temp folder under `/tmp`, which only your user can open and which is removed when the job ends: it is `$TMPDIR` in the worker's commands, its file tools can read and write it by path, and the worker is told to use it instead of `/tmp`, as a native session is told of its scratchpad. An env file written there is read like one in any other working directory, so its values are replaced before anything is forwarded. Worker commands cannot read or write the temp files of other Claude Code sessions under `/tmp/claude-<uid>`.

The worker and its commands read `.env` and other `.env*` files inside its working directories (the consented directories and their linked worktrees) as a native subagent does, so tests and scripts that load `.env.local` work. Editing or writing one follows the native rules of the accepted mode: default mode asks, Accept edits allows, auto mode's classifier judges, and `.envrc` always asks. On Linux and macOS, the worker’s sandbox denies env files outside the working directories. Their values never reach Tenjin or DeepSeek: in every forwarded request, the worker's result, its activity rows, the local progress file and a stopped worker's last activity, each value becomes `[env:NAME]`, the variable's name. The worker knows which variable was there but not its value, so it cannot copy or edit a value in place. Tenjin reads every `.env*` file in the working directories, skipping `node_modules` and `.git`, when it starts the worker. Where the system watches folders for changes (macOS and Windows), a worker prepared while its offer is open starts its Claude Code from the last complete scan this session made of the same directories, and its own full scan runs meanwhile: it gets no assignment until that scan has ended and found nothing its starting denies leave open. Such a kept scan is held in the Tenjin process's memory only, like every scan, until a newer one replaces it or the session ends. If a worker warmed before acceptance on Windows or without a recursive watcher, Tenjin scans again before giving it the assignment. A scan that needs new read denies makes Tenjin start a fresh worker. Before each request it rechecks the files it knows and the folders that hold them, and on macOS and Windows it also watches for new ones. Tenjin reads and parses each changed file in full, up to 16 MiB. If a file is too large or Tenjin cannot read or parse it at startup, Linux and macOS workers run with that file denied. Windows workers require a complete scan before startup. If a new or changed env file becomes unreadable, unparseable or too large during a job, Tenjin stops forwarding and ends the job with `env_file_unscanned`. A folder it cannot list has its contents denied to the worker's commands and its env files to the file tools, since a command could still open one by name. A folder that held an env file and can no longer be listed during the job stops forwarding the same way, with `env_file_unscanned`. A scan that cannot finish keeps every env file denied for that job. The values are held in memory only, never logged or saved.

Known limits of the value replacement: values under 8 characters, and bare words or numbers under 16 such as `development`, `localhost` or `3000`, are sent as written. URLs without credentials are sent as written unless their path or query holds a value that would itself be replaced; a URL with a user name or password is replaced whole. Free-text comments are sent as written; a commented-out `KEY=value` line is replaced. A value is matched as parsed, as written in the file, line by line when it spans lines, and URL-encoded, JSON-escaped or base64-encoded whole. Any other form can pass: a hash, hex, base64 of text that contains the value (such as an HTTP Basic header), or a fragment of a one-line value. On Linux there is no watcher: a new env file in a folder that is not a working directory's top level and held no env file at job start is found only when the worker reads it by name, or at the next job.

On Linux and macOS, GitHub access comes from a per-job token, never from your GitHub config files or keychain: Tenjin's own process reads it with `gh auth token` and gives it to that worker's `gh` and git over HTTPS only, with a per-job gh config and a git config holding just your name, email and a GitHub credential helper. To give workers a narrower token, set `TENJIN_WORKER_GITHUB_TOKEN`, or `TENJIN_WORKER_GITHUB_TOKEN_FILE` naming a file that holds it, where Claude Code starts; a named token that cannot be read gives workers no GitHub token rather than your login. With either variable set, the session's own `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN` and `GITHUB_ENTERPRISE_TOKEN` are cleared in the worker's environment, so only the named token is there. The job's GitHub settings also outrank a GitHub token in your Claude Code settings `env`, which Claude Code would otherwise hand the worker's commands, and no token is put on the worker's command line. A fine-grained token needs Metadata read, Contents read and write, Pull requests read and write, Issues read and write, Commit statuses read and Actions read, plus Workflows read and write only if a worker may change `.github/workflows/`. Tenjin replaces the token's value in everything it forwards to Tenjin and DeepSeek, in the worker's result and in its activity rows. A command can still print or send it to an allowed host, so prefer the narrower token. The sandbox preapproves GitHub, GitHub’s content and Actions log hosts, the npm registry and nodejs.org, subject to Claude Code’s settings. For other hosts, default mode prompts, auto mode can allow the host for the command, and bypass mode can allow it without a prompt. A strict sandbox allowlist blocks hosts outside it. [Claude Code network settings](https://code.claude.com/docs/en/settings-reference#sandboxnetworkstrictallowlist) On macOS the worker's sandbox may also reach the system certificate trust service, which `gh` needs to check TLS certificates.

The worker keeps the permission mode the parent had when the offer was accepted, for the whole job; a later prompt, mode switch or `cd` in the parent does not stop it. In auto mode the worker's own classifier judges each call that needs a decision, and a call that would still need a person is refused at once with its reason, in words about that one call, so the worker never waits on you and does not give the tool up. Every worker command runs in the sandbox, which refuses a read outside your consented directories at the read itself. A second check reads a command's text before it runs, and asks about a command whose paths it cannot work out, such as `cd <worktree> && git status --short | head -20 && git diff main...HEAD --stat`. In auto mode that ask is refused like any other, because answering it yes would run the whole command, whatever else it holds, without the classifier's verdict; the refusal tells the worker to run the `cd` as its own call or to use `git -C <path>`, and that form is judged and runs. A command that names a path outside your consented directories stays refused, and so does an ask about one part of a compound command, which can stand for one of your own ask rules. Under a bypass-permissions parent the worker runs in bypass mode inside the same sandbox and read limits and never asks you, and that one ask is answered yes there, since bypass mode judges no call and the sandbox still refuses the outside read; a plan-mode parent keeps work native. In default mode it asks you, with Allow once, Allow for this job or Deny. That dialog waits for your answer for as long as the job may run, as a native permission prompt waits; a session that has closed answers no. Only your own choice in it allows a call: nothing the parent writes to a worker, in its assignment or a follow-up, is a permission or changes the worker's mode, rules or sandbox, and Tenjin sets up no hook that could answer the dialog for you. The worker runs as the native agent the parent asked for, `general-purpose`, `Explore` or a custom agent whose definition qualifies (see below), with the prompt and tools Claude Code gives a native subagent of that type. Before the worker starts, Tenjin starts the same Claude Code for a moment, with no hooks or MCP servers and no model call leaving your machine, has it launch that subagent, and reads the prompt from the subagent's first request. Tenjin's MCP server keeps that read for up to 10 minutes, for the same Claude Code binary, agent type, definition, root and working directories, and reads it again as soon as one of those changes or any settings, plugin list, agent definition, CLAUDE.md or rules file it depends on changes. That prompt carries the note Claude Code gives its own subagents: messages from the agent that launched it direct its work and are never your consent or approval. When the prompt cannot be read, the worker starts with Claude Code's main prompt and that note, and Tenjin's MCP server logs why. As a native subagent of its type does, the worker gets the repository's git status unless it runs as `Explore`, and tool search as your session has it: MCP tools and the less used built-in tools are loaded when the worker asks for them. A native subagent uses the parent's MCP servers, which are already connected, so the worker does not wait for its own to connect before its first turn: a server that connects later announces its tools, and tool search loads them from then on. Your hooks and the plugins' hooks run in the worker as they run in a native subagent. Its tool, permission and stop events run them as your session does, with the same matchers, order, timeouts and blocks. It runs no `SessionStart` hook when it starts or resumes, and no `UserPromptSubmit` hook for its prompts, as a native subagent runs none, so the context those hooks add stays out of it. A `SessionStart` after a compaction still runs, as it does in a native subagent, and so does every hook in managed settings. An `Explore` worker starts without your CLAUDE.md and rules files, global, project and local, as a native `Explore` subagent does; one in a folder below the working directory still reaches it when it reads a file there, as it reaches a native one. As a native subagent, it has no tool for asking you questions in any mode. A worker starts no subagent, native or DeepSeek, and none of its calls is held or offered. Unlike a native subagent, it has none of Tenjin's own tools (`request`, `approve`, `subagent`): what a worker pays for is its model calls and its web searches, which count in its job's budget, and a Tenjin lookup of its own would not. This holds for every name Tenjin's server is registered under: a Tenjin server that starts inside a worker lists only the tool its hooks call, which answers nothing there. A worker that needs something from you ends with its report, and the parent continues it. Pushes, force pushes, branch deletions, merges and every other action go through that mode's own permission flow, exactly as a native subagent's do. One thing is refused in every mode, as part of keeping secrets out: a credential probe the sandbox cannot stop by path, which is the keychain (`security`), git's credential helpers (`git credential`, `git-credential-*`) and a GitHub token printed by `gh auth token`, `gh auth git-credential` or `gh auth … --show-token`. A worker that stops early returns its last text and recent activity to the parent.

## Accept, cancel and continue

The parent calls its native subagent tool normally. A native subagent's own Agent (or legacy Task) call, at any depth of native agents, is judged and offered as the main conversation's is, with the session's context followed by that subagent's own conversation, and that subagent accepts the offer or keeps it native (the worker it accepts draws its row in that subagent's transcript, and its DeepSeek agent is listed under that subagent); it stays native when the subagent's tools leave out `subagent`, when it or an agent above it may run in a permission mode of its own, or when it works in a folder of its own such as a worktree, since a worker runs in the session's mode and workspace. A DeepSeek worker's own calls get no offer. Each call is judged by itself, as each native call is its own work: several calls in one response, and calls made while other offers are open or other workers run, each get their own offer, in any turn, whether a prompt or a task notification started it. One exception: where no prompt was typed since Tenjin's process started (a resumed session woken by a notification), the first subagent call runs natively, and Tenjin learns the session and its permission mode from that call's own hook. No count limit applies beyond each job's ceiling and your daily budget. Every offer carries the full parent policy and starts no worker. Accept one offer with `subagent({offer_id})`. To start multiple workers together, accept the chosen offers with one `subagent({offer_ids: [id1, id2]})` call. Each offer keeps its own permissions, budget, and cancellation, and the call returns one result per offer in the order requested. Two workers in a batch can run inference at the same time. Any additional workers wait for an inference lane. Claude Code runs separate acceptance calls in order. Claude preloads this tool so acceptance needs no ToolSearch turn. To keep an offer native, the parent sends the same Agent (or legacy Task) call again unchanged. In every permission mode it then runs natively, as sent, with no second routing fee; Tenjin never rewrites it. Key order, whitespace around a field's text, and a field at its default (`false`, `null`, or `subagent_type: "general-purpose"`) are not changes. Any other change makes a new call, which may be offered again. The repeat counts once per offer, in the same session and workspace and from the same agent, until the offer expires 15 minutes after it was made; when its worker was accepted and then stopped or never started, for 15 minutes after that. After it, the offer can no longer be accepted. When several open offers hold identical calls, one repeat keeps one of them native, the oldest first, and the others stay open. A second identical call in the same model response is not a repeat: it was written before the first offer was read, so it gets its own offer. Saved consent covers its stated disclosure/inference scope; binding restrictions, repository risk judgment and normal tool asks still apply.

On a router that supports refunds, each Claude worker run opens its own inference channel when it first needs to pay. When the worker finishes, stops, or fails, Tenjin closes that channel and returns its unused USDC to the funding wallet. If the refund is still pending, Tenjin retries it during the session and when a Claude session starts. `tenjin balance` shows pending and confirmed refunds recorded on this installation. A refund still pending at a router you configured earlier is listed with that router's address, and is retried only while that router is the configured one. Each fresh deposit counts against the existing automatic spend limits as it is sent. When the router's receipt and the chain confirm a refund, its amount comes off the daily budget's count again, so the budget counts what the run cost and not its deposit. A pending refund stays counted. A refund gives back no more than that run's own deposits still count, and nothing once the budget's 24-hour window has rolled, since that window no longer holds the deposit. A job's own ceiling counts its calls, not its deposits, so a refund changes nothing there. Older routers still use shared inference channels, and `tenjin balance` lists their remaining credit. So does a router whose answer to the question about refunds is not its refund terms: nothing is signed for that question, so the job runs on the shared channels.

A call for a custom agent type can be offered when you or the project wrote its definition, a file in the job root's own `.claude/agents` or in your `~/.claude/agents`, and it pins no model (`model: inherit` pins none) and sets only `name`, `description`, `tools`, `disallowedTools`, `color` and `effort`. The worker then runs as that agent: the definition's prompt, as Claude Code gives it to a native subagent, in place of the general one, and its tools. Its effort stays high whatever the definition says. A definition that pins a model, or sets a permission mode, isolation, background running, memory, hooks, MCP servers or skills, runs natively. So does every agent a plugin provides (such as `codex:codex-rescue`), whatever its definition says, every built-in type other than `general-purpose` and `Explore`, and a definition in a folder above the job's root: their prompts are not yours or the project's to send to DeepSeek. A definition whose frontmatter Tenjin cannot read exactly as Claude Code does (a quoted key such as `'tools': [Read]`, a bracketed list over several lines, a repeated key, an empty tool list) also runs natively, so a tool limit is never lost on the way to a worker. A call that names its agent (`name`), runs in the background, resumes another agent or asks for isolation also stays native: a named call starts a teammate and returns at once, which the accept call cannot do.

`tenjin config subagents why` lists why recent subagent calls got no offer, newest first: the time, the tool (with `from a subagent` when a native subagent made the call), the session id, and a reason code such as `input_filter:name`, `permission_mode:plan`, `caller_unqualified:tools`, `over_size_limit` with the byte count, `server_declined` with the router's code, or `kept_native`. The record holds no assignment text, is kept for 7 days in a file only your user can read, and is sent nowhere. It is written only while subagent routing is on.

Cancel an offer or active worker with `subagent({cancel: offer_id})`, or interrupt the host. Turning routing off prevents new paid requests; cancel to drain active work. An offer is accepted by its id in any turn of the session that received it, until it expires 15 minutes after it was made, and it or its worker is cancelled by that id at any time. Another session gets nothing for that id.

Accepting the same offer again never starts a second worker and adds no charge. While its worker runs, the repeat is refused. After the worker ended, a repeat in any later turn of the same session returns the stored result: the completed result, or for a stopped worker how it ended, its last text and recent steps, the next step, and the spend as it then stands. That read is local and free.

A worker stops when its session ends or its Tenjin process restarts, as a native subagent does. No worker runs on after the session closes. When you resume the same session, a finished worker's result can still be read, and the worker continued by its handle. A worker that was still running when the session ended is reported as stopped, with the reason `interrupted`, and cannot be continued; send the work again if you still need it.

A background Agent call (`run_in_background`) is offered as a foreground call is. When the parent accepts it, the worker runs in the background, as a native background agent does: the accept call returns at once with `status: "started"`, the parent's turn goes on, and the worker's row reads `Backgrounded agent (↓ to manage)` until it ends, then its end line. When the worker ends, the Tenjin plugin hands its result to the parent as a message, which starts a turn when the session is idle and waits for the running turn otherwise; its row reads `› Message from @DeepSeek (ctrl+o to expand)`. That message is the job's stored result, the same one a foreground accept returns, with its status, counts, spend and worker handle. Claude Code gives a plugin's own agent no completion notice, so the message is the plugin's and not a task notification. The job's budget, consent checks, causes of ending and cancel are those of a foreground job; the parent session's end stops the worker; and sending the original call again unchanged keeps it native, in the background as written. A batch accept can mix foreground and background offers: it returns when its foreground workers end, and names each background worker as started; a background worker that ended meanwhile has its message sent once the batch call has returned. If the session was resumed or the plugin reloaded before the message came, accepting the offer again returns the stored result. Calls that set `resume`, `name`, `team_name` or `isolation` stay native.

An individual offer appears on its held Agent row, with the native name struck through and `Tenjin offered DeepSeek` with its cap after it, as a held web search shows the tool Tenjin offered. When the parent accepts the offer, the worker's `DeepSeek(<description>)` row replaces that row in place, and the accept call adds no row of its own. The compact row disappears once the offer is kept native by repeating the call, cancelled, or expired. Claude Code draws two or more Agent calls of one response as its own `agents finished` summary, which a plugin cannot redraw or remove, so those calls have no row to replace. When the parent accepts their offers, the DeepSeek rows follow that summary with no other line. A call of that response that did not run and is sent again and held again changes nothing. When the parent does anything else with an offer of the group (it repeats a call to keep it native, cancels an offer, or ends its turn with one not accepted), or when a call was held with no offer, Tenjin adds a notice below that group with the number of held calls that did not run natively. The parent does not check on a running worker: its result arrives by itself, and the plugin refuses the parent model's own call of the viewer's activity read. A worker whose call sits in that summary draws a `DeepSeek(<description>)` row at the accept call; two or more of them draw one DeepSeek agent group with an entry and live status for each worker. Ctrl+O shows the held call with its offer, and the worker's row and result at the accept call. Each worker shows its progress from the moment of accept: `starting` and the time waited until its Claude Code has started, then its tool uses, tokens, time and the spend settled so far while it runs, with its latest step under it. It ends with a `Done (…)` line like a native subagent's; when it did not complete, the line says who or what ended it: `Stopped by you (…)`, `Cancelled by the parent (…)`, `Interrupted (…)` when Claude Code ended the call that ran it, `Session ended (…)`, `Time limit reached (…)` or `Budget reached (…)`, `Model call failed (…)`, `Model call timed out (…)` or `Payment refused (…)` when a model call through Tenjin returned no result, `DeepSeek unavailable (…)` when DeepSeek could not take the request, and `Stopped (…)` for anything else; `Not started (…)` when it never started. The worker's result to the parent carries the same cause as a fixed code (`endedBy`) with a sentence in plain words, and `status: "stopped"`, or `"unknown"` only when nothing said why; a failed model call also carries, in its stop reason, the router's HTTP status, the router's own error code (such as `invalid_model_request`) or the payer's code (such as `payment_failed`, the router answered the paid request with an error) when one is known, and the worker's last text. The line's word, time and counts are the job's own, read from the CLI's record when the row was not following the worker (after a reload or a resumed session). If no read can say how the job ended, the line reads `Outcome not shown here (…)` with the counts seen so far and no time: the result still returns to the parent. Claude Code moves a tool call that runs longer than two minutes to a background task: the worker runs on, its row stays live, and when it ends the row shows its end line, and the task's notification reads `› Message from @DeepSeek (ctrl+o to expand)`, as a native subagent's return does, and in full `DeepSeek "<description>" finished · Done (…)`. The parent receives the worker's result with that notification. On supported Claude Code versions, use the native Down-arrow agent selector and Enter to open the running DeepSeek agent; its row in the agent list reads `DeepSeek` and the task's description, with ` (2)` on a second task of the same description. Its first message is the worker's assignment, the prompt the parent sent, as a native subagent's is; after a restart it reads `DeepSeek worker for: <description>`. Its transcript is written as the worker goes, one step for each worker reply, as a native subagent's is: the worker's own text, then its calls drawn by Claude Code as its own, such as `Read(src/a.ts)` with `Read 120 lines` under it, `Bash(pnpm lint)` with the first three lines of its output, `WebFetch(<url>)` with Claude Code's own `Received <size> (200 OK)` line, or `Exa page read(<url>)` when the local fetch failed and Exa page read read the page, `Exa search("<query>")` with Claude Code's `Did 1 search in <time>` line, as the router's own rows name those tools, or `Update(src/a.ts)`, and a refused or failed call's reason under its row; a tool search draws nothing, as a native one does, and Claude Code folds read-only commands into its own `Searched for …` line as it does a native subagent's. A call of another tool is a text line with the first line of its result. At the end come the worker's answer and a `Done (…)` line with its counts; a worker that never started says `Not started`. The spinners in that view and in the parent's are Claude Code's own. That transcript is a local record in Claude Code's own session files, as a native subagent's transcript is, with the job's GitHub token and env file values already replaced as they stood when each step was written; of a call's output it holds only those short lines, never a file's content. Claude Code's own background-agent summary reads that transcript, as it reads a native subagent's. Tenjin's own data folder keeps no live worker activity after a job: the CLI holds it in memory, and its local display file is removed when the job ends. It keeps each handback, so a later accept in the same session can return it: a completed worker's result, and a stopped worker's last text and up to 24 recent steps, with the same replacements already made, in files only your user can read. A shell call's command is shown on your machine only and is not added to what is forwarded to Tenjin or DeepSeek, nor to a stopped worker's handback. While a worker runs, the mod holds only the rows not yet written into the transcript, up to 2,000. Above the prompt, one status line gives the model, the worker's state, its tool uses and tokens, and the spend settled so far, then the final accounted spend once it ends. Stopping that agent from the agent list cancels its owned worker, as stopping a native subagent does; leaving or closing its view, or Claude Code ending its turn, does not. Worker operations appear as activity rows; the work result returns separately to the parent, and continuations retain the full worker history.

Before reloading or removing Tenjin, wait for the parent's Tenjin call to finish or confirm cancellation, and for its native activity agent to stop. A stop acknowledgement alone does not confirm both have drained. Removing or reloading the mod while the viewer is active can let Claude call its own model outside the DeepSeek worker budget.

Completed Claude workers return a `tenjin-worker-…` handle. The same parent can continue with native `SendMessage`, or compatible `Agent.resume`. Each full follow-up is held until the parent runs it with one `subagent({offer_id})` call or stops it with `subagent({cancel: offer_id})`; the parent does not judge again whether the worker suits it, as a native follow-up resumes its subagent with no confirmation. Because the text goes to DeepSeek, what binds an assignment still binds a follow-up: your own instructions that restrict the worker's model, privacy, disclosure or paid inference, and planning, which stays native; the parent cancels a follow-up that would break one. A follow-up pays no routing fee, and its inference is charged to what is left of the original job's ceiling. It reopens the same history, for up to 7 days after the worker's last run, including after the same session is resumed. Stop a continuation by cancelling its offer; a worker handle is never sent to native tools. Current instructions and permissions refresh. Missing history/accounting, uncertain state, changed directory scope or revoked disclosure refuses continuation. Native retention may remove history; no idle worker service is maintained. Each run also leaves a diagnostic record beside its job: the worker's tools and MCP servers, its root and commit, the output cap, thinking mode and reasoning its requests carried, its repeat reminders and retries, the time of each start phase from the accept to its first reply, and how it ended. It holds names and counts only. For a job that did not complete it also holds the error: the job's end code, and the class name, code and first 300 characters of the message of the error and its causes, with secret-shaped values masked, also when the job ended before its worker started. It is readable by your user alone and is sent nowhere. Tenjin removes its own local job, conversation, budget, handback and diagnostic records 7 days after their last write.

On Windows, native tools and shell commands use the shared Claude profile and the account’s own Git and CLI credentials. Windows ACLs govern reads and writes by shell commands. Tenjin rechecks the worker grant and masks recognized secrets before forwarding tool results.

## Charges and limits

A valid offered job incurs one routing fee: 15% of expected inference spend, capped at $0.003, even if declined. Several calls in a turn mean several offers and several routing fees, one each; your daily budget and spend limits apply to every fee, and each job keeps its own ceiling. A fee your limits refuse buys no offer, and that call runs natively. A call the router judges should stay native pays no fee. Sending an offered call again unchanged to keep it native adds no second fee. A follow-up to a finished worker is not a new offer and pays no routing fee. Inference uses reported tokens plus the 5% proxy fee. Quotes reserve the requested output allowance and a conservative input bound; final usage can be lower. Provider overruns remain Tenjin's exposure and cannot increase the accepted quote. A worker's Messages request asks for up to 65,536 output tokens and reserves at least $0.083866 at the current peak tariff before additional system/tools/history input. Configuration refuses a job ceiling below $0.086866, including the maximum routing fee; this necessary floor does not guarantee a larger prompt fits. A continuing job must retain enough unspent ceiling for each next call's full quote. Inference is refused if its quote exceeds the remaining ceiling; a routing fee may already be paid. A job's cap is your per-call spend limit or a lower ceiling you named, so no inference deposit passes the per-call limit; the daily budget and creator allowlist still apply, and a per-call limit of zero stops jobs as it stops every automatic payment. Other connected services retain their own permissions and billing. A worker cannot call Tenjin's paid-tool router or purchase tool itself; its web searches, below, are the only tool calls Tenjin pays for on its behalf.

A worker's web search is a paid Tenjin tool call, never sent to DeepSeek. Tenjin answers the worker's native WebSearch itself with Exa search at its lite tier: $0.004 a search, with no routing fee, paid from your Tenjin wallet within your per-call limit and daily budget, as any lookup is, and listed in `tenjin payments`. The job reserves the catalog's $0.007 price ceiling for the search before anything is signed and then counts what was paid, so searches are part of the job's ceiling, its spend and its end line. A search the job's remaining ceiling or your limits cannot cover is refused with nothing paid, and so is one Tenjin's router does not offer; the worker's WebSearch then returns a plain error, `Web search is not available to this worker right now`, with the reason, and the job continues. A payment that may have left without a settled amount keeps its full reservation, as an uncertain model call does. WebFetch stays native: Claude Code fetches the page on your machine. Only when that fetch fails on the network, with an HTTP error status, or on an empty page does Tenjin read the page through Exa page read, $0.001 with no routing fee, paid and counted the same way, and hand the page's text to the worker beside the failed result, up to 60,000 characters. A page on this machine or a private network, and an address that holds a replaced secret value, is never sent to Exa. Your `tenjin config block` and `only` rules apply to these searches and page reads as they apply to what Tenjin picks on its own: one that leaves Exa out, such as a block of Exa, of Tenjin's own tools or of the task or category the search serves, or an `only` rule that names none of them, refuses the search with that plain error and reads no page, with nothing paid. A preference never forbids a service, so it changes nothing here. When such a rule cannot be checked because Tenjin's router cannot be reached and no earlier copy of its names is kept, the search is refused the same way. Any other request the worker's Claude Code makes that Tenjin cannot send fails alone, as an API error for that one request, with nothing sent or paid. That includes a request offering more than 256 tools, the most one request to Tenjin's router may carry; the error names the count. With tool search on, tools load as the worker asks for them, so a request rarely offers that many.

Tenjin refills inference credit as needed, normally depositing up to $0.25 at a time. If one quote requires more than $0.25 in additional credit, Tenjin deposits only the amount that quote needs within the job and daily limits. Smaller deposits leave more USDC available for other workers.

At current peak rates plus 5%, a worker's Messages quote, with its 65,536-token output cap, is about $0.084 plus $0.32 per decimal MB of request body through about 1.04 MB, then caps near $0.413 at the model's input-context limit. Budget left after actual spend and unresolved reservations must cover each next full quote; these are reservation estimates, not actual charges or a guaranteed run.

Uncertain signed requests keep their full reservation until reconciled; recovery does not buy a replacement. Reconciling is a free read of Tenjin's own record of each such call, made while the job has no run going: before a follow-up is offered, and when a stopped worker's handback is read again. A call Tenjin finished is counted at its actual cost. A call that failed or was cancelled with nothing charged is released, so it no longer lowers what the job can still spend. A call the router says DeepSeek failed, or whose reply the router cut after its idle limit or its deadline, is read the same way at once, so when nothing was charged it is released; a cut reply is never tried again. A call the router confirms cost nothing (it never reached the router, the router answered a rate limit or a server error before any payment, or DeepSeek failed it and nothing was charged) is tried again, as the DeepSeek harness does: up to 5 tries, waiting 0.5 s doubling to 10 s with some jitter, or as long as the router's `Retry-After` asks. An uncertain or charged call is never tried again, nor a request refused as malformed; when the tries run out the job ends with that call's cause. A model reply is read through 2,000,000 bytes. To a router whose offer says it honours a stated size of at least 2,000,000 bytes, each Messages call states the size the worker then reads (`maxResultBytes`), the smaller of the router's size and 4,000,000 bytes, and that router fails a larger reply before it charges for it. Any other answer, or none, keeps the full reservation. `subagent` reports completion, elapsed time, tool uses, tokens, accounted spend and unresolved reservations. Timeout or interruption is not proof of settlement. Jobs have a 40-minute wall limit and no turn limit, as the DeepSeek harness has none; native compaction remains enabled. A worker has no separate start-up window, as a native subagent has none: its Claude Code takes the time the machine needs to start, inside the job's wall limit, and MCP servers keep connecting while it works. Cancel or interrupt a start that takes too long. A worker still starting when the wall limit passes reports `not_started`. So does a job whose first question to the router, whether it refunds the run's own channel, got no answer in three tries (`endedBy: "router_unreachable"`). In each case no inference was bought, the routing fee for the offer was already paid, and sending the original call again unchanged runs it natively with no second fee.

Claude Code is primary and requires a qualified installed version with observed Manual, Accept edits, Auto, `dontAsk` or bypass-permissions mode. In auto mode the worker's native classifier runs on Flash. Plan mode, a bypass mode that settings disable, and unavailable modes stay native.

Codex uses the router's existing experimental support. Only independent foreground calls with explicit `fork_turns: "none"`, fully covered native access and the existing Never/user approval policy qualify. Other modes and history-inheriting calls stay native. Codex worker resume and background-agent UI are outside this pilot.
