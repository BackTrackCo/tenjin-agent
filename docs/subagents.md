# DeepSeek subagents

Tenjin can offer DeepSeek V4.1 Flash 1017 for helper work. Your parent keeps its model and final accept/veto. Ordinary implementation and scoped review can qualify; planning stays native. Repository instructions and model/privacy restrictions still apply.

## Setup and controls

Fresh installations enable eligible DeepSeek routing for each session's qualified native workspace, with a $1 total routing/inference ceiling per job. The existing setup question and receipt explain sharing. Opening another repository uses that session's current native scope; the folder where installation ran supplies no directory grant. Each job freezes its qualified scope and rechecks it before tools, inference and continuation.

Existing users keep their settings, including off choices and named-directory consent. Updating, refreshing or adding another host does not enable DeepSeek for an existing profile. The parent still accepts or vetoes each offer.

```sh
tenjin config subagents off
tenjin config subagents on --repository /path/to/repository --max-job 1
```

The explicit `on --repository` command records consent for the named directory and descendants, the configured router origin, recipients and job ceiling. Repeat for another repository to retain both, or name a containing workspace. This selects named-directory scope instead of following future workspaces automatically. Local GitHub origin names for qualifying directories and their direct child repositories accompany offers so the parent can match GitHub tasks to paths. Names grant no filesystem permission or additional disclosure scope; stale names are dropped when their local origins change or disappear. A project can disable routing, but cannot grant consent or raise your money limits. Unsupported older consent must be renewed explicitly. That includes a consent given before a worker could read your `~/.claude` folder (see Data and permissions): it stops qualifying, no offer is made, `tenjin config subagents why` shows `consent_outdated`, and running the `on --repository` command again shows the current terms and renews it for the directories you name.

## Data and permissions

Routing sends the assignment and bounded parent context to Tenjin and TypeSafe before acceptance. A routing request is at most 16 KB: Tenjin gives up parent context to fit it, the oldest message first, and never cuts the assignment, so a call whose assignment alone is larger stays native. After acceptance, applicable instructions, assignments and tool results reach DeepSeek through Tenjin. Known secrets are masked; sensitive prose is not guaranteed anonymous. Server replay content expires after 24 hours; financial and continuation authorization records persist.

The Claude worker retains native settings, rules, hooks, MCPs, CLIs and tool permissions in its workspace, including uncommitted changes. Global auto-memory is disabled for this worker. Native-workspace consent follows the host's qualified current directories and access exceptions. Named-directory consent makes every named directory a working directory too, so a session in one repository of a named workspace reaches its sibling repositories; their linked git worktrees inside the named directories are added at job start, so the worker can commit in them. A native additional directory outside the named directories is denied to the worker and listed in the offer, and the offer still stands; native read or write exceptions outside them keep work native. Workspace-only shell reads must be enforceable: Windows, managed-only read-path policies, disabled or excluded sandbox commands, and startup paths containing `*`, `?`, `[` or `]` keep work native. Scope is checked before assignment, tool use and inference. Your parent's endpoint, saved login and Remote Control stay in place. Unsupported authority or host-controlled authentication keeps work native. A provider refusal at worker startup can follow an already-paid routing fee.

The worker loads your global Claude Code configuration as a native session does, so your personal `~/.claude/CLAUDE.md` is in its instructions. As a native subagent can, its file tools and commands read the skills, plugins (with their data folders), agents, commands and rules under `~/.claude`, every session transcript and project memory under `~/.claude/projects`, your prompt history `~/.claude/history.jsonl`, and your `~/.claude/settings.json` and `settings.local.json`; they cannot write them. What it reads there, other projects' sessions and memory included, can reach Tenjin and DeepSeek. The values in those settings files' `env` blocks, and in the `env` block Claude Code hands to the worker's commands, become `[env:NAME]` by the env file rules below: the files are read when the job starts and again before anything is forwarded, a settings file that cannot be parsed at the start stays unreadable, and one that stops parsing during the job stops it. Transcripts and history are not scanned, so a secret pasted or printed in an earlier session is sent as written unless it has a known token shape. The rest of `~/.claude` stays closed: the credentials file, settings backups (whose old values are not scanned), session state such as `debug` and `file-history`, `tenjin-loops` outside your consented directories and a skill's files where its folder links outside `~/.claude`; so do `~/.claude.json` and other repositories' Claude settings inside a named directory. Each job has its own temp folder under `/tmp`, which only your user can open and which is removed when the job ends: it is `$TMPDIR` in the worker's commands, its file tools can read and write it by path, and the worker is told to use it instead of `/tmp`, as a native session is told of its scratchpad. An env file written there is read like one in any other working directory, so its values are replaced before anything is forwarded. Worker commands cannot read or write the temp files of other Claude Code sessions under `/tmp/claude-<uid>`.

The worker and its commands read `.env` and other `.env*` files inside its working directories (the consented directories and their linked worktrees) as a native subagent does, so tests and scripts that load `.env.local` work. Editing or writing one follows the native rules of the accepted mode: default mode asks, Accept edits allows, auto mode's classifier judges, and `.envrc` always asks. Env files outside the working directories stay unreadable. Their values never reach Tenjin or DeepSeek: in every forwarded request, the worker's result, its activity rows, the local progress file and a stopped worker's last activity, each value becomes `[env:NAME]`, the variable's name. The worker knows which variable was there but not its value, so it cannot copy or edit a value in place. Tenjin reads every `.env*` file in the working directories, skipping `node_modules` and `.git`, when the job starts. Before each request it rechecks the files it knows and the folders that hold them, and on macOS and Windows it also watches for new ones. A file is read and parsed whole each time it changes, whatever its size up to 16 MiB, so a file that grows during the job stays covered. A file it cannot parse has every line of 8 or more characters replaced. A file over 16 MiB or one it cannot read stays denied when it is there at job start, and the job runs without it. One that appears or grows past 16 MiB during the job can no longer be denied, so the job forwards and shows nothing more and ends with the stop reason `env_file_unscanned`. A folder it cannot list has its contents denied to the worker's commands and its env files to the file tools, since a command could still open one by name. A scan that cannot finish keeps every env file denied for that job. The values are held in memory only, never logged or saved.

Known limits of the value replacement: values under 8 characters, and bare words or numbers under 16 such as `development`, `localhost` or `3000`, are sent as written. URLs without credentials are sent as written unless their path or query holds a value that would itself be replaced; a URL with a user name or password is replaced whole. Free-text comments are sent as written; a commented-out `KEY=value` line is replaced. A value is matched as parsed, as written in the file, line by line when it spans lines, and URL-encoded, JSON-escaped or base64-encoded whole. Any other form can pass: a hash, hex, base64 of text that contains the value (such as an HTTP Basic header), or a fragment of a one-line value. On Linux there is no watcher: a new env file in a folder that is not a working directory's top level and held no env file at job start is found only when the worker reads it by name, or at the next job.

GitHub access comes from a per-job token, never from your GitHub config files or keychain: Tenjin's own process reads it with `gh auth token` and gives it to that worker's `gh` and git over HTTPS only, with a per-job gh config and a git config holding just your name, email and a GitHub credential helper. To give workers a narrower token, set `TENJIN_WORKER_GITHUB_TOKEN`, or `TENJIN_WORKER_GITHUB_TOKEN_FILE` naming a file that holds it, where Claude Code starts; a named token that cannot be read gives workers no GitHub token rather than your login. With either variable set, the session's own `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN` and `GITHUB_ENTERPRISE_TOKEN` are cleared in the worker's environment, so only the named token is there. A fine-grained token needs Metadata read, Contents read and write, Pull requests read and write, Issues read and write, Commit statuses read and Actions read, plus Workflows read and write only if a worker may change `.github/workflows/`. Tenjin replaces the token's value in everything it forwards to Tenjin and DeepSeek, in the worker's result and in its activity rows. A command can still print or send it to an allowed host, so prefer the narrower token. Worker commands reach GitHub, GitHub's content and Actions log hosts, the npm registry and nodejs.org without asking; another host asks you in default mode and is denied in auto and bypass mode. On macOS the worker's sandbox may also reach the system certificate trust service, which `gh` needs to check TLS certificates.

The worker keeps the permission mode the parent had when the offer was accepted, for the whole job; a later prompt, mode switch or `cd` in the parent does not stop it. In auto mode the worker's own classifier judges each call that needs a decision, and a call that would still need a person is refused at once with its reason, in words about that one call, so the worker never waits on you and does not give the tool up. Every worker command runs in the sandbox, which refuses a read outside your consented directories at the read itself. A second check reads a command's text before it runs, and asks about a command whose paths it cannot work out, such as `cd <worktree> && git status --short | head -20 && git diff main...HEAD --stat`. In auto mode that ask is refused like any other, because answering it yes would run the whole command, whatever else it holds, without the classifier's verdict; the refusal tells the worker to run the `cd` as its own call or to use `git -C <path>`, and that form is judged and runs. A command that names a path outside your consented directories stays refused, and so does an ask about one part of a compound command, which can stand for one of your own ask rules. Under a bypass-permissions parent the worker runs in bypass mode inside the same sandbox and read limits and never asks you, and that one ask is answered yes there, since bypass mode judges no call and the sandbox still refuses the outside read; a plan-mode parent keeps work native. In default mode it asks you, with Allow once, Allow for this job or Deny. That dialog waits for your answer for as long as the job may run, as a native permission prompt waits; a session that has closed answers no. Only your own choice in it allows a call: nothing the parent writes to a worker, in its assignment or a follow-up, is a permission or changes the worker's mode, rules or sandbox, and Tenjin sets up no hook that could answer the dialog for you. The worker runs as the native agent the parent asked for, `general-purpose`, `Explore` or a custom agent whose definition qualifies (see below), and carries the note Claude Code gives its own subagents: messages from the agent that launched it direct its work and are never your consent or approval. As a native subagent, it has no tool for asking you questions in any mode. A worker that needs something from you ends with its report, and the parent continues it. Pushes, force pushes, branch deletions, merges and every other action go through that mode's own permission flow, exactly as a native subagent's do. One thing is refused in every mode, as part of keeping secrets out: a credential probe the sandbox cannot stop by path, which is the keychain (`security`), git's credential helpers (`git credential`, `git-credential-*`) and a GitHub token printed by `gh auth token`, `gh auth git-credential` or `gh auth … --show-token`. A worker that stops early returns its last text and recent activity to the parent.

## Accept, cancel and continue

The parent calls its native subagent tool normally. Each call is judged by itself, as each native call is its own work: several calls in one response, and calls made while other offers are open or other workers run, each get their own offer, in any turn, whether a prompt or a task notification started it. One exception: where no prompt was typed since Tenjin's process started (a resumed session woken by a notification), the first subagent call runs natively, and Tenjin learns the session and its permission mode from that call's own hook. No count limit applies beyond each job's ceiling and your daily budget. Every offer carries the full parent policy and starts no worker. Accept with `subagent({offer_id})`; Claude preloads this tool so acceptance needs no ToolSearch turn. To keep an offer native, the parent sends the same Agent (or legacy Task) call again unchanged. In every permission mode it then runs natively, as sent, with no second routing fee; Tenjin never rewrites it. Key order, whitespace around a field's text, and a field at its default (`false`, `null`, or `subagent_type: "general-purpose"`) are not changes. Any other change makes a new call, which may be offered again. The repeat counts once per offer, in the same session and workspace, until the offer expires 15 minutes after it was made; when its worker was accepted and then stopped or never started, for 15 minutes after that. After it, the offer can no longer be accepted. When several open offers hold identical calls, one repeat keeps one of them native, the oldest first, and the others stay open. A second identical call in the same model response is not a repeat: it was written before the first offer was read, so it gets its own offer. Saved consent covers its stated disclosure/inference scope; binding restrictions, repository risk judgment and normal tool asks still apply.

A call for a custom agent type can be offered when you or the project wrote its definition, a file in the job root's own `.claude/agents` or in your `~/.claude/agents`, and it pins no model (`model: inherit` pins none) and sets only `name`, `description`, `tools`, `disallowedTools`, `color` and `effort`. The worker then runs as that agent: the definition's prompt in place of the general one, and its tools. Its effort stays high whatever the definition says. A definition that pins a model, or sets a permission mode, isolation, background running, memory, hooks, MCP servers or skills, runs natively. So does every agent a plugin provides (such as `codex:codex-rescue`), whatever its definition says, every built-in type other than `general-purpose` and `Explore`, and a definition in a folder above the job's root: their prompts are not yours or the project's to send to DeepSeek. A definition whose frontmatter Tenjin cannot read exactly as Claude Code does (a quoted key such as `'tools': [Read]`, a bracketed list over several lines, a repeated key, an empty tool list) also runs natively, so a tool limit is never lost on the way to a worker. A call that names its agent (`name`), runs in the background, resumes another agent or asks for isolation also stays native: a named call starts a teammate and returns at once, which the accept call cannot do.

`tenjin config subagents why` lists why recent subagent calls got no offer, newest first: the time, the tool, the session id, and a reason code such as `input_filter:name`, `permission_mode:plan`, `over_size_limit` with the byte count, `server_declined` with the router's code, or `kept_native`. The record holds no assignment text, is kept for 7 days in a file only your user can read, and is sent nowhere. It is written only while subagent routing is on.

Cancel an offer or active worker with `subagent({cancel: offer_id})`, or interrupt the host. Turning routing off prevents new paid requests; cancel to drain active work. An offer is accepted by its id in any turn of the session that received it, until it expires 15 minutes after it was made, and it or its worker is cancelled by that id at any time. Another session gets nothing for that id.

Accepting the same offer again never starts a second worker and adds no charge. While its worker runs, the repeat is refused. After the worker ended, a repeat in any later turn of the same session returns the stored result: the completed result, or for a stopped worker how it ended, its last text and recent steps, the next step, and the spend as it then stands. That read is local and free.

A worker stops when its session ends or its Tenjin process restarts, as a native subagent does. No worker runs on after the session closes. When you resume the same session, a finished worker's result can still be read, and the worker continued by its handle. A worker that was still running when the session ended is reported as stopped, with the reason `interrupted`, and cannot be continued; send the work again if you still need it.

An offer appears on the held Agent row as `Tenjin offered DeepSeek` with its cap; nothing has run yet. Once the offer is accepted, kept native by sending the call again, cancelled or expired, that row draws nothing, so the task has one row: the worker's, or the native call's own. The parent does not check on a running worker: its result arrives by itself, and the plugin refuses the parent model's own call of the viewer's activity read. An accepted worker draws one `DeepSeek(<description>)` row from the moment of accept: `starting` and the time waited until its Claude Code has started, then its tool uses, tokens, time and the spend settled so far while it runs, with its latest step under it. It ends with a `Done (…)` line like a native subagent's; when it did not complete, the line says who or what ended it: `Stopped by you (…)`, `Cancelled by the parent (…)`, `Interrupted (…)` when Claude Code ended the call that ran it, `Session ended (…)`, `Time limit reached (…)` or `Budget reached (…)`, `Model call failed (…)`, `Model call timed out (…)` or `Payment refused (…)` when a model call through Tenjin returned no result, `DeepSeek unavailable (…)` when DeepSeek could not take the request, and `Stopped (…)` for anything else; `Not started (…)` when it never started. The worker's result to the parent carries the same cause as a fixed code (`endedBy`) with a sentence in plain words, and `status: "stopped"`, or `"unknown"` only when nothing said why; a failed model call also carries, in its stop reason, the router's HTTP status or the payer's code (such as `payment_failed`, the router answered the paid request with an error) when one is known, and the worker's last text. The line's word, time and counts are the job's own, read from the CLI's record when the row was not following the worker (after a reload or a resumed session). If no read can say how the job ended, the line reads `Outcome not shown here (…)` with the counts seen so far and no time: the result still returns to the parent. Claude Code moves a tool call that runs longer than two minutes to a background task: the worker runs on, its row stays live, and when it ends the row shows its end line, and the task's notification reads `› Message from @DeepSeek (ctrl+o to expand)`, as a native subagent's return does, and in full `DeepSeek "<description>" finished · Done (…)`. The parent receives the worker's result with that notification. On supported Claude Code versions, use the native Down-arrow agent selector and Enter to open the running DeepSeek agent. Its first message is the worker's assignment, the prompt the parent sent, as a native subagent's is; after a restart it reads `DeepSeek worker for: <description>`. Its transcript shows the run as a native subagent's does: each tool call as a row such as `Read(src/a.ts)` or `Bash(pnpm lint)`, a refused or failed call's reason under its row, the worker's own text between calls, and at the end the worker's answer and a `Done (…)` line with its counts. While the worker runs, its latest rows are drawn in that agent's transcript area, above its spinner, and grow as it works; the parent's spinner stays Claude Code's own, as it does while a native subagent runs. When it ends, the whole run is written into that transcript, so it stays readable afterwards, and a worker that never started says `Not started`. That transcript is a local record in Claude Code's own session files, as a native subagent's transcript is, with the job's GitHub token and env file values already replaced; a successful call's output is not copied into it. Tenjin's own data folder keeps no live worker activity after a job: the CLI holds it in memory, and its local display file is removed when the job ends. It keeps each handback, so a later accept in the same session can return it: a completed worker's result, and a stopped worker's last text and up to 24 recent steps, with the same replacements already made, in files only your user can read. A shell call's command is shown on your machine only and is not added to what is forwarded to Tenjin or DeepSeek, nor to a stopped worker's handback. While a worker runs, the mod holds up to 2,000 of its rows or 512 KiB, whichever is less, and lets them go once the transcript is written. Above the prompt, one status line gives the model, the worker's state, its tool uses and tokens, and the spend settled so far, then the final accounted spend once it ends. Stopping that agent from the agent list cancels its owned worker, as stopping a native subagent does; leaving or closing its view, or Claude Code ending its turn, does not. Worker operations appear as activity rows; the work result returns separately to the parent, and continuations retain the full worker history.

Before reloading or removing Tenjin, wait for the parent's Tenjin call to finish or confirm cancellation, and for its native activity agent to stop. A stop acknowledgement alone does not confirm both have drained. Removing or reloading the mod while the viewer is active can let Claude call its own model outside the DeepSeek worker budget.

Completed Claude workers return a `tenjin-worker-…` handle. The same parent can continue with native `SendMessage`, or compatible `Agent.resume`. Each full follow-up is held until the parent runs it with one `subagent({offer_id})` call or stops it with `subagent({cancel: offer_id})`; the parent does not judge again whether the worker suits it, as a native follow-up resumes its subagent with no confirmation. Because the text goes to DeepSeek, what binds an assignment still binds a follow-up: your own instructions that restrict the worker's model, privacy, disclosure or paid inference, and planning, which stays native; the parent cancels a follow-up that would break one. A follow-up pays no routing fee, and its inference is charged to what is left of the original job's ceiling. It reopens the same history, for up to 7 days after the worker's last run, including after the same session is resumed. Stop a continuation by cancelling its offer; a worker handle is never sent to native tools. Current instructions and permissions refresh. Missing history/accounting, uncertain state, changed directory scope or revoked disclosure refuses continuation. Native retention may remove history; no idle worker service is maintained. Tenjin removes its own local job, conversation, budget and handback records 7 days after their last write.

## Charges and limits

A valid offered job incurs one routing fee: 15% of expected inference spend, capped at $0.003, even if declined. Several calls in a turn mean several offers and several routing fees, one each; your daily budget and spend limits apply to every fee, and each job keeps its own ceiling. A fee your limits refuse buys no offer, and that call runs natively. A call the router judges should stay native pays no fee. Sending an offered call again unchanged to keep it native adds no second fee. A follow-up to a finished worker is not a new offer and pays no routing fee. Inference uses reported tokens plus the 5% proxy fee. Quotes reserve the requested output allowance and a conservative input bound; final usage can be lower. Provider overruns remain Tenjin's exposure and cannot increase the accepted quote. A usual 32K-output Messages request reserves at least $0.041611 at the current peak tariff before additional system/tools/history input. Configuration refuses a job ceiling below $0.044611, including the maximum routing fee; this necessary floor does not guarantee a larger prompt fits. A continuing job must retain enough unspent ceiling for each next call's full quote. Inference is refused if its quote exceeds the remaining ceiling; a routing fee may already be paid. The separately approved job ceiling controls inference deposits rather than the tool router's positive per-call limit; the daily budget, creator allowlist and an explicit zero automatic-spend stop still apply. Other connected services retain their own permissions and billing. Tenjin's paid-tool router and purchase tool do not run inside these workers.

At current peak rates plus 5%, a 32K-output Messages quote is about $0.04 plus $0.32 per decimal MB of request body through about 1.04 MB, then caps near $0.371 at the model's input-context limit. Budget left after actual spend and unresolved reservations must cover each next full quote; these are reservation estimates, not actual charges or a guaranteed run.

Uncertain signed requests keep their full reservation until reconciled; recovery does not buy a replacement. Reconciling is a free read of Tenjin's own record of each such call, made while the job has no run going: before a follow-up is offered, and when a stopped worker's handback is read again. A call Tenjin finished is counted at its actual cost. A call that failed or was cancelled with nothing charged is released, so it no longer lowers what the job can still spend. A call the router says DeepSeek failed is read the same way at once, so when nothing was charged it is released before the job ends. Any other answer, or none, keeps the full reservation. `subagent` reports completion, elapsed time, tool uses, tokens, accounted spend and unresolved reservations. Timeout or interruption is not proof of settlement. Jobs have a 40-minute wall limit and Claude's 500-turn emergency guard; native compaction remains enabled. A worker has no separate start-up window, as a native subagent has none: its Claude Code takes the time the machine needs to start, inside the job's wall limit, and MCP servers keep connecting while it works. Cancel or interrupt a start that takes too long. A worker still starting when the wall limit passes reports `not_started`. Either way no inference was bought, the routing fee for the offer was already paid, and sending the original call again unchanged runs it natively with no second fee.

Claude Code is primary and requires a qualified installed version with observed Manual, Accept edits, Auto, `dontAsk` or bypass-permissions mode. In auto mode the worker's native classifier runs on Flash. Plan mode, a bypass mode that settings disable, and unavailable modes stay native.

Codex uses the router's existing experimental support. Only independent foreground calls with explicit `fork_turns: "none"`, fully covered native access and the existing Never/user approval policy qualify. Other modes and history-inheriting calls stay native. Codex worker resume and background-agent UI are outside this pilot.
