# DeepSeek subagents

Tenjin can offer DeepSeek V4.1 Flash 1017 for helper work. Your parent keeps its model and final accept/veto. Ordinary implementation and scoped review can qualify; planning stays native. Repository instructions and model/privacy restrictions still apply.

## Setup and controls

Fresh installations enable eligible DeepSeek routing for each session's qualified native workspace, with a $1 total routing/inference ceiling per job. The existing setup question and receipt explain sharing. Opening another repository uses that session's current native scope; the folder where installation ran supplies no directory grant. Each job freezes its qualified scope and rechecks it before tools, inference and continuation.

Existing users keep their settings, including off choices and named-directory consent. Updating, refreshing or adding another host does not enable DeepSeek for an existing profile. The parent still accepts or vetoes each offer.

```sh
tenjin config subagents off
tenjin config subagents on --repository /path/to/repository --max-job 1
```

The explicit `on --repository` command records consent for the named directory and descendants, the configured router origin, recipients and job ceiling. Repeat for another repository to retain both, or name a containing workspace. This selects named-directory scope instead of following future workspaces automatically. Local GitHub origin names for qualifying directories and their direct child repositories accompany offers so the parent can match GitHub tasks to paths. Names grant no filesystem permission or additional disclosure scope; stale names are dropped when their local origins change or disappear. A project can disable routing, but cannot grant consent or raise your money limits. Unsupported older consent must be renewed explicitly.

## Data and permissions

Routing sends the assignment and bounded parent context to Tenjin and TypeSafe before acceptance. After acceptance, applicable instructions, assignments and tool results reach DeepSeek through Tenjin. Known secrets are masked; sensitive prose is not guaranteed anonymous. Server replay content expires after 24 hours; financial and continuation authorization records persist.

The Claude worker retains native settings, rules, hooks, MCPs, CLIs and tool permissions in its workspace, including uncommitted changes. Global auto-memory is disabled for this worker. Native-workspace consent follows the host's qualified current directories and access exceptions. Named-directory consent makes every named directory a working directory too, so a session in one repository of a named workspace reaches its sibling repositories; their linked git worktrees inside the named directories are added at job start, so the worker can commit in them. A native additional directory outside the named directories is denied to the worker and listed in the offer, and the offer still stands; native read or write exceptions outside them keep work native. Workspace-only shell reads must be enforceable: Windows, managed-only read-path policies, disabled or excluded sandbox commands, and startup paths containing `*`, `?`, `[` or `]` keep work native. Scope is checked before assignment, tool use and inference. Your parent's endpoint, saved login and Remote Control stay in place. Unsupported authority or host-controlled authentication keeps work native. A provider refusal at worker startup can follow an already-paid routing fee.

Worker file tools and commands cannot read credential-bearing native config, history or private controller data, including other repositories' Claude settings inside a named directory. Ordinary skill, agent, command and support files remain usable under the current native permissions.

The worker and its commands read `.env` and other `.env*` files inside its working directories (the consented directories and their linked worktrees) as a native subagent does, so tests and scripts that load `.env.local` work. Editing or writing one follows the native rules of the accepted mode: default mode asks, Accept edits allows, auto mode's classifier judges, and `.envrc` always asks. Env files outside the working directories stay unreadable. Their values never reach Tenjin or DeepSeek: in every forwarded request, the worker's result, its activity rows, the local progress file and a stopped worker's last activity, each value becomes `[env:NAME]`, the variable's name. The worker knows which variable was there but not its value, so it cannot copy or edit a value in place. Tenjin reads every `.env*` file in the working directories, skipping `node_modules` and `.git`, when the job starts. Before each request it rechecks the files it knows and the folders that hold them, and on macOS and Windows it also watches for new ones. A file it cannot parse has every line of 8 or more characters replaced, a file it cannot read in full stays denied, and a scan that cannot finish keeps every env file denied for that job. The values are held in memory only, never logged or saved.

Known limits of the value replacement: values under 8 characters, and bare words or numbers under 16 such as `development`, `localhost` or `3000`, are sent as written. URLs without credentials are sent as written unless their path or query holds a value that would itself be replaced; a URL with a user name or password is replaced whole. Free-text comments are sent as written; a commented-out `KEY=value` line is replaced. A value is matched as parsed, as written in the file, line by line when it spans lines, and URL-encoded, JSON-escaped or base64-encoded whole. Any other form can pass: a hash, hex, base64 of text that contains the value (such as an HTTP Basic header), or a fragment of a one-line value. On Linux there is no watcher: a new env file in a folder that is not a working directory's top level and held no env file at job start is found only when the worker reads it by name, or at the next job.

GitHub access comes from a per-job token, never from your GitHub config files or keychain: Tenjin's own process reads it with `gh auth token` and gives it to that worker's `gh` and git over HTTPS only, with a per-job gh config and a git config holding just your name, email and a GitHub credential helper. To give workers a narrower token, set `TENJIN_WORKER_GITHUB_TOKEN`, or `TENJIN_WORKER_GITHUB_TOKEN_FILE` naming a file that holds it, where Claude Code starts; a named token that cannot be read gives workers no GitHub token rather than your login. A fine-grained token needs Metadata read, Contents read and write, Pull requests read and write, Issues read and write, Commit statuses read and Actions read, plus Workflows read and write only if a worker may change `.github/workflows/`. Tenjin replaces the token's value in everything it forwards to Tenjin and DeepSeek, in the worker's result and in its activity rows. A command can still print or send it to an allowed host, so prefer the narrower token. Worker commands reach GitHub, GitHub's content and Actions log hosts, the npm registry and nodejs.org without asking; another host asks you in default mode and is denied in auto and bypass mode. On macOS the worker's sandbox may also reach the system certificate trust service, which `gh` needs to check TLS certificates.

The worker keeps the permission mode the parent had when the offer was accepted, for the whole job; a later prompt, mode switch or `cd` in the parent does not stop it. In auto mode the worker's own classifier judges each call that needs a decision, and a call that would still need a person is denied with its reason, so the worker never waits on you. Under a bypass-permissions parent the worker runs in bypass mode inside the same sandbox and read limits and never asks you; a plan-mode parent keeps work native. In default mode it asks you, with Allow once, Allow for this job or Deny. In every mode it never runs keychain or git credential probes, `gh auth token`, a push to `main` or `master`, a force push, a branch deletion or a merge. A worker that stops early returns its last text and recent activity to the parent.

## Accept, cancel and continue

The parent calls its native subagent tool normally. Every offer carries the full parent policy and starts no worker. Accept with `subagent({offer_id})`; Claude preloads this tool so acceptance needs no ToolSearch turn. To keep an offer native, the parent sends the same Agent (or legacy Task) call again unchanged. In every permission mode it then runs natively, as sent, with no second routing fee; Tenjin never rewrites it. Key order, whitespace around a field's text, and a field at its default (`false`, `null`, or `subagent_type: "general-purpose"`) are not changes. Any other change makes a new call, which may be offered again. The repeat counts once per offer, in the same session and workspace: for the rest of that turn, and in later turns until the offer expires 15 minutes after it was made. After it, the offer can no longer be accepted. Saved consent covers its stated disclosure/inference scope; binding restrictions, repository risk judgment and normal tool asks still apply.

Cancel an offer or active worker with `subagent({cancel: offer_id})`, or interrupt the host. Turning routing off prevents new paid requests; cancel to drain active work. Repeated acceptance does not start a second worker.

An offer appears on the held Agent row as `Tenjin offered DeepSeek` with its cap; nothing has run yet. An accepted worker draws one `DeepSeek(<description>)` row that shows its tool uses, tokens, time and the spend settled so far while it runs, with its latest step under it, and ends with a `Done (…)` line like a native subagent's. On supported Claude Code versions, use the native Down-arrow agent selector and Enter to open the running DeepSeek agent. Its Tenjin activity panel shows recent worker tool calls/results, the spend settled so far and, once it ends, final accounted spend. Stopping that agent cancels its owned worker. Worker operations appear as activity rows; the work result returns separately to the parent, and continuations retain the full worker history.

Before reloading or removing Tenjin, wait for the parent's Tenjin call to finish or confirm cancellation, and for its native activity agent to stop. A stop acknowledgement alone does not confirm both have drained. Removing or reloading the mod while the viewer is active can let Claude call its own model outside the DeepSeek worker budget.

Completed Claude workers return a `tenjin-worker-…` handle. The same parent can continue with native `SendMessage`, or compatible `Agent.resume`. Each full follow-up is held for accept/veto, then reopens the same history and original budget across days. Decline a continuation by cancelling its offer; a worker handle is never sent to native tools. Current instructions and permissions refresh. Missing history/accounting, uncertain state, changed directory scope or revoked disclosure refuses continuation. Native retention may remove history; no idle worker service is maintained.

## Charges and limits

A valid offered job incurs one routing fee: 15% of expected inference spend, capped at $0.003, even if declined. Sending its call again unchanged to keep it native adds no second fee. Inference uses reported tokens plus the 5% proxy fee. Quotes reserve the requested output allowance and a conservative input bound; final usage can be lower. Provider overruns remain Tenjin's exposure and cannot increase the accepted quote. A usual 32K-output Messages request reserves at least $0.041611 at the current peak tariff before additional system/tools/history input. Configuration refuses a job ceiling below $0.044611, including the maximum routing fee; this necessary floor does not guarantee a larger prompt fits. A continuing job must retain enough unspent ceiling for each next call's full quote. Inference is refused if its quote exceeds the remaining ceiling; a routing fee may already be paid. The separately approved job ceiling controls inference deposits rather than the tool router's positive per-call limit; the daily budget, creator allowlist and an explicit zero automatic-spend stop still apply. Other connected services retain their own permissions and billing. Tenjin's paid-tool router and purchase tool do not run inside these workers.

At current peak rates plus 5%, a 32K-output Messages quote is about $0.04 plus $0.32 per decimal MB of request body through about 1.04 MB, then caps near $0.371 at the model's input-context limit. Budget left after actual spend and unresolved reservations must cover each next full quote; these are reservation estimates, not actual charges or a guaranteed run.

Uncertain signed requests keep their full reservation until reconciled; recovery does not buy a replacement. `subagent` reports completion, elapsed time, tool uses, tokens, accounted spend and unresolved reservations. Timeout or interruption is not proof of settlement. Jobs have a 40-minute wall limit and Claude's 500-turn emergency guard; native compaction remains enabled. A worker has no separate start-up window, as a native subagent has none: its Claude Code takes the time the machine needs to start, inside the job's wall limit, and MCP servers keep connecting while it works. Cancel or interrupt a start that takes too long. A worker still starting when the wall limit passes reports `not_started`. Either way no inference was bought, the routing fee for the offer was already paid, and sending the original call again unchanged runs it natively with no second fee.

Claude Code is primary and requires a qualified installed version with observed Manual, Accept edits, Auto, `dontAsk` or bypass-permissions mode. In auto mode the worker's native classifier runs on Flash. Plan mode, a bypass mode that settings disable, and unavailable modes stay native.

Codex uses the router's existing experimental support. Only independent foreground calls with explicit `fork_turns: "none"`, fully covered native access and the existing Never/user approval policy qualify. Other modes and history-inheriting calls stay native. Codex worker resume and background-agent UI are outside this pilot.
