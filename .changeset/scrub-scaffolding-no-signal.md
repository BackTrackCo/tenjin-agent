'tenjin-cli': patch

The dispatch hook and the WebFetch push arm stop scrubbing paths, hostnames and other identifiers out of a search query: search availability wins over sanitizing away the best search key the server has, while a credential-shaped value is still never one of those keys.

Both `dispatchQuestion` and `fetchQuestion` used to build a search query by scrubbing a subagent prompt or a fetched URL of anything shaped like a path, a hostname or a secret, on the theory that only prose should leave the machine. That traded away the one thing most likely to make a lookup land: the server now does identifier-aware BM25 retrieval, and a path or a hostname is exactly what it matches on. It also produced its own failure mode (tenjin-agent#197): when the one topic-bearing run in a prompt or URL was itself path- or entropy-shaped, scrubbing it away left bare connective prose ("a question", "for a question about it") that read as a short real question while carrying no signal — production lookups traced back to exactly that literal, used for years as this suite's own query fixture.

The two arms now split on what each one is actually protecting against, and both land on the same floor. `dispatchQuestion` (the Task/Agent dispatch arm) scrubs only SECRET-shaped tokens — a Task prompt can embed an API key that is not otherwise outbound, and a team-shelf miss forwards this same query to the public marketplace, so a credential still cannot ride along. Paths, hostnames and other identifiers in a dispatch prompt now ship too. `scrub()` gained a `mode: 'secretsOnly'` argument for this.

`fetchQuestion` (the WebFetch push arm) first shipped this round with scrubbing dropped entirely — the URL has already left the machine via the fetch itself, so scrubbing our own search copy of it seemed to protect nothing. Round-2 review found the gap in that reasoning: a credential can sit in the url's PATH (`acme.com/download/sk-live-.../file.pdf`), which is not the query string the fetch's own request-side allow-list guards, and `fetchQuestion`'s path→words conversion had no filter of its own over it — so a credential there rode the marketplace query whole, on a team-shelf miss to the public one. `fetchQuestion` now runs the same `scrub(combined, 'secretsOnly')` as every other arm: paths and hostnames still ship unchanged (a hostname never enters `words` in the first place, so it was never at risk), and only a credential, control byte or email comes out. This does not reopen the quadratic host-rule risk the no-scrub trade also happened to close: `secretsOnly` returns before the path/host rules ever run, so the arm still never executes `SECRET_HOST_RE` over attacker-influenced input.

The floor this arm used to apply below 20 characters of post-scrub content is gone along with the residue it was gating on: with paths and hostnames no longer stripped, a short question built around one no longer collapses to scaffolding, so there's nothing left to floor. What remains is the trivial case — an empty or whitespace-only result — and the existing guard against composing a description-only query with a dangling colon when a prompt scrubs to nothing.

**The policy now covers every knowledge/search arm, not just dispatch.** Full privacy-tier scrubbing is retired everywhere search-query or published-knowledge text is built: the prompt hook (a typed prompt becoming the team+public search query), the churn arm (a file basename becoming a package-gotcha query), the findings harvest (a subagent's captured finding becoming a queued publish draft) and the failure arm's local pairing/Fix-post material (`signatureOf`'s dedup key, `safeCommand`'s stored/replayed command, and the scrubbed error line `tenjin sync` reads into a Fix post's title and body) all now call `scrub(text, 'secretsOnly')`. Paths, hostnames, IPv4 literals, basenames and git SHAs ship everywhere on this list; only credentials, control bytes and emails are removed. `scrub()` itself gained changes to support this: the email rule now runs in `secretsOnly` mode too (an email is PII, not a search key, so it is dropped in both modes); the entropy rule's replacement is skipped — in `secretsOnly` mode only — for a match that is entirely lowercase `[0-9a-f]`, which is the shape of a git SHA (full mode still drops it; a hex-only API token is the accepted, deliberate trade for keeping a commit SHA search-able); and, merged in from tenjin-agent#262, an ALL_CAPS env-var-shaped entropy match (`DATABASE_URL`-style, bounded at 64 characters) now survives in _either_ mode — it is an identifier exactly like a path or a host, not a value.

**Merged with tenjin-agent#262's condensed-query pipeline.** That PR landed on `main` while this one was in flight and changed what the prompt arm builds its query from: instead of slicing the scrubbed prompt at 400 characters, it now runs `identifiersOf()` over the scrubbed text to pull out PR/issue refs, file names, env-var names and other identifier-shaped tokens, then `condense()` to build a query of those identifiers first and the prompt's own words (stopwords and short clauses dropped) after, capped at 24 tokens/400 characters — and sends an `identifiers` array beside `query` on the wire. This changeset's policy now sits underneath that pipeline rather than replacing it: the prompt arm scrubs with `scrub(prompt, 'secretsOnly')` first, so paths, hostnames, basenames and git SHAs are still in the text `identifiersOf`/`condense` read, and a credential or an email is already gone before either function ever sees it. Concretely: **no secret, credential or email reaches `query` or `identifiers`; a path, a hostname, a basename, a git SHA or an env-var name deliberately rides in both** — that is the whole point of ranking on identifiers instead of prose. A test in `push-scripts.test.ts` fixtures an `sk-`-style key inside a prompt and asserts it lands in neither field.

Along the way this fixed a live bug in the churn arm — though not the one a `.sh`/`.io` basename would suggest. The churn/read arms only ever scrub a `.js/.jsx/.ts/.tsx/.mjs/.mts/.cjs/.py` basename (an unrelated, pre-existing extension gate: those are the only source files `packagesInSource` understands), and none of those extensions is itself a TLD, so a literal `deploy.sh` never reached this scrub call at all. The real collision is one level in: full-mode scrub's hostname rule has no anchors, so it matches a TLD-shaped label ANYWHERE in a basename, and `test`, `dev`, `app`, `co` and `local` are all in that TLD list and all ordinary naming segments in an allowed extension — `checkout.test.ts` (this very suite's own naming convention), `app.config.dev.ts` and similar scrubbed to nothing, and the arm's own `wordCount(query) < 1` guard silenced it: the churn trigger sent no request at all, with no error and no row, for any churned `*.test.ts` file. `secretsOnly` doesn't run the hostname rule, so the segment now survives long enough for the existing `.replace(/\.[^.]+$/, '')` to strip the real extension as intended.

`tenjin publish`'s own `scanDraft()` and `tenjin sync`'s own `scan()`/`survivesTeamDrop()` are unaffected and remain the secrets/PII backstop (block/warn) at actual publish time for both paths — this change is about what a search query or a stored draft carries before that gate, not about removing the gate. One bound of that backstop is on record: neither scanner has a rule for a hex-only token, so the git-SHA trade extends past search queries — a hex-only API key in a recorded command line can ride into a team-shelf Fix post ungated. Accepted for now by owner call (Fix posts reach only the internal team shelf, never the public marketplace); the follow-up is tracked in tenjin-agent#281.

Existing installs keep whatever hook script `tenjin install` last wrote; this change only reaches a machine that reinstalls or upgrades the hooks (`tenjin install`).
